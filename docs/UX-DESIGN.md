# 풀어봄 UX: 문장으로 이해하고, 값을 바꾸고, 결과로 확인하기

설계·구현일: 2026-10-20 (Asia/Seoul). 대상은 현재 VS Code 확장 기능입니다.

## 결정

**문서형 읽기를 기본으로, 수정에는 카드·비교 표를, 관계에는 구조 다이어그램을 사용하는 혼합형**으로 구성합니다. 형식 선택부터 요구하지 않고, 사용자가 하려는 일에 맞는 표현을 제공합니다.

사용자가 언급한 ‘PyTorch 느낌’은 코드·실행·결과를 블록 단위로 오가는 기술 도구형 경험으로 해석했습니다. PyTorch 자체를 특정 편집기 UI로 간주하지 않습니다.

| 후보 | 잘하는 일 | 첫 사용에서 생길 수 있는 부담 | 적용 |
| --- | --- | --- | --- |
| 기술 도구·노트북형 | 실험을 반복하고 결과를 비교하기 | 실행 환경, 코드 셀, 변수 상태를 먼저 알아야 할 수 있음 | 확인 단계의 예시 입력·결과에 활용 |
| 긴 글 중심 | 처음 보는 내용을 차례로 이해하기 | 바꿀 위치와 여러 결과의 차이를 찾기 어려움 | 기본 설명으로 사용하되 기능 하나씩 읽기 |
| 표 중심 | 값과 조건, 변경 전후를 정확히 비교하기 | 맥락과 중첩 관계를 읽기 어려움 | 규칙 목록과 입력별 결과 비교에 활용 |
| 그래프 중심 | 갈림길과 파일 연결을 파악하기 | 큰 그래프는 탐색과 해석부터 배워야 할 수 있음 | 필요할 때 선택한 기능의 구조와 파일 관계 보기 |

이 표의 부담 평가는 설계 판단입니다. 본 제품의 비개발자 사용자 실험 결과는 아닙니다.

## 사용 흐름과 구현

### 1. 이해하기

- 현재 읽는 파일과 저장 전 변경 포함 여부를 작은 문맥 영역에 유지합니다.
- 기능이 하나면 바로 설명합니다. 여러 개면 이름으로 고르고, 많으면 검색·더 보기로 접근합니다.
- 선택한 기능의 **받는 정보 → 내부 설명 → 근거 코드**를 한곳에 보여 줍니다.
- 기본은 문장입니다. ‘구조 흐름’은 같은 구문에서 읽은 중첩·분기·반환·오류·후처리를 상자로 보여 줍니다. 실제 실행 기록과 구별합니다.
- 구조 표시의 깊이·개수 한도에서 내용이 생략되면 이를 표시하고 문장/원문으로 안내합니다.
- 전체 상세 설명, 프로젝트 용어, 원본 구조는 펼쳐 볼 수 있습니다. JSON·HTML·CSS·SQL 및 언어별 기존 읽기 기능도 유지합니다.

### 2. 바꾸기

- ‘값 선택 → 새 값 입력 → 차이 확인·적용’으로 현재 진행 위치를 표시합니다.
- 규칙은 읽기 쉬운 목록 카드로 보여 줍니다. 긴 코드 이름과 원본 줄 번호도 함께 유지합니다.
- 넓은 패널에서는 목록과 편집 영역을 나란히 놓습니다. 좁은 패널에서는 세로로 배치하고 선택한 편집 입력으로 포커스를 옮깁니다.
- 값의 유형에 따라 숫자 입력, 여러 줄 문구, 의미 설명을 붙인 선택지를 제공합니다.
- 변경안에는 ‘아직 적용하지 않음’, 현재/새 값, 문법 검사 범위, 코드 차이 보기, 예시별 결과 비교, 적용을 함께 배치합니다.
- 새 값을 다시 입력하거나 선택·문서가 바뀌면 이전 변경안을 제거합니다. 입력 도중 도착한 오래된 응답도 다시 표시하지 않습니다.
- 적용 뒤에는 실행 취소 방법과 ‘확인하기’로 가는 다음 행동을 보여 줍니다.
- 문장 요청은 별도 펼침 영역에 둡니다. 직접 선택과 같은 호스트의 수정·검증 경로를 사용합니다.

### 3. 확인하기

- 읽기 화면에서 고른 기능을 예시 입력 표로 확인할 수 있습니다.
- VS Code의 실제 알림과 구문 검토 항목을 구분합니다. 알림 0개를 ‘검증 완료’로 표현하지 않습니다.
- 프로젝트 검사·성능 측정, JSON 인자 직접 입력은 필요할 때 펼칩니다.
- 예시 계산 결과가 나타나면 결과 영역으로 키보드 포커스를 옮겨 이어서 읽을 수 있게 합니다.

### 보조 도구

‘연결 지도’와 ‘AI 도움’은 읽기·수정·확인의 세 주요 경로와 시각적으로 구분합니다. 기존 로컬 모델 선택, 제안 검토, 프로젝트 검사를 유지합니다. AI 결과를 원문에서 확인한 사실과 같은 것으로 표시하지 않습니다.

## 시각·접근성 기준

- VS Code의 테마·글꼴·대비 색상을 따릅니다. UI 미리보기의 밝은 녹색은 검증용 테마 예시입니다.
- 제목, 설명, 근거, 보조 안내의 위계를 분명히 하고 반복되는 카드·경고를 줄입니다.
- 파일 전체를 읽기 전에 용어 설정이나 모델 설치를 요구하지 않습니다.
- 360px의 좁은 패널에서 본문이 가로로 넘치지 않도록 합니다. 비교 표와 관계 그래프처럼 넓이가 필요한 영역만 내부 스크롤을 사용합니다.
- 입력에 레이블을 제공하고, 선택 상태·진행 단계·비교 전후를 색 이외의 문구로도 표시합니다.
- 줄 번호 버튼의 클릭 영역, 키보드 포커스, 동작 줄이기 설정을 고려합니다.

## 근거와 검증 범위

[NN/g의 복잡한 애플리케이션 지침](https://www.nngroup.com/articles/complex-application-design/)은 필요한 시점에 옵션을 드러내는 방식으로 복잡성을 줄일 것을 권합니다. [Microsoft의 카드 설계 지침](https://adaptivecards.microsoft.com/?topic=design-best-practices)도 과도한 요소를 줄이고 정보를 점진적으로 제시하도록 안내합니다. 이전 [Consensus 연구 정리](RESEARCH.md)의 직접 조작·자연어 병행, 원본 근거 연결, 변경 전후 확인 원칙을 유지했습니다.

실제 분석 Worker를 연결한 브라우저 하네스로 화면·입력·비교·언어·폭을 확인합니다. 하네스의 VS Code 연결 부분은 모의 구현이므로 실제 편집기 검증과 구분합니다. 실제 호스트 검증은 기존 VS Code 통합 테스트로 수행합니다. 실행 명령과 결과는 `UX-VALIDATION.md`에 기록합니다.

## 다음 사용자 평가

비개발자에게 설명 없이 다음 과제를 수행하게 합니다: 배송비 계산 조건 찾기, 무료 배송 기준 50000을 70000으로 바꾸기, 어떤 입력의 배송비가 달라지는지 찾기, 원본 근거로 이동하기, 적용 후 되돌리기. 도움 요청·완료 시간·잘못된 적용·결과 해석 오류를 기록합니다. 사용자가 ‘문법 통과’를 ‘전체 동작 보장’으로 오해하는지도 확인합니다. 실제 평가 이전에는 이해도나 성공률 향상 수치를 주장하지 않습니다.
