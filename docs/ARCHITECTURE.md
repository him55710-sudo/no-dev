# 풀어봄 구조와 확장 순서

## 0.7 개발판의 로컬 AI 경로

`src/core/localAssistant.ts`는 언어·요청·응답 크기와 구조, 실제 원문 인용, 겹치지 않는 변경 범위를 검증한다. `extension/src/ollama.ts`는 확장 호스트에서 고정 루프백으로 연결하며, 클라우드 비활성화와 로컬 모델 메타데이터 확인 후에만 현재 파일을 전송한다. 파일/모델/요청 선택은 `extension/ui/LocalAssistant.tsx`에서 수행한다. 코드·답변에 포함된 도구나 명령은 실행하지 않는다.

`localAssistantController.ts`는 문서 URI·버전·전체 원문과 요청 문맥을 보관하고, 변경 시 요청을 취소하고 결과를 무효화한다. JS/TS와 JSON 제안은 분석 Worker에서 문법 확인한다. Python은 `pythonValidation.ts`의 고정 `ast.parse` 프로그램으로만 검사한다. native diff → 명시적 적용 → 기존 undo 경로를 사용하며 모델이 적용 권한을 갖지 않는다. 이 경로는 데스크톱 로컬 작업 공간 전용이며 브라우저 데모에는 포함하지 않는다. [제약과 실제 증거](LOCAL_AI.md).

## 0.5 화면 구조와 문구 편집

`core/jsx.ts`는 TypeScript AST를 별도 UI 구조로 바꾼다. JSX 리터럴의 엔티티와 공백은 실행 없는 컴파일 후 문자열 읽기로 복원한다. `InterfaceTree`는 경량 데이터만 받아 두 환경에서 렌더링하며, 숨긴 하위 구조는 펼칠 때 생성한다. 원시 JSX 문구·속성은 문자열 표현식으로 바뀌어 입력이 마크업이나 코드로 해석되지 않는다. 원문 범위·문법 검사·오래된 변경안 거부·실행 취소 경로는 기존 편집기와 공유한다. [상세 범위](INTERFACE.md).

## 0.4 프로젝트 용어

`glossary.ts`는 길이·수량·제어 문자 검증과 언어별 갱신을 담당하는 가벼운 모델입니다. Worker의 `terminology.ts`는 사용자 용어가 있는 파일에만 TypeScript checker를 만들어 선언과 참조를 연결합니다. 파일 외부 라이브러리·의존성은 읽지 않으며 전체 타입 검사를 수행하지 않습니다. 캐시는 원문과 해당 파일의 정규화한 용어를 함께 비교합니다.

`Terminology.tsx`를 브라우저와 VS Code에서 공유합니다. 웹은 IndexedDB의 작업 공간에 저장하고 새 프로젝트에서 비웁니다. 확장은 workspaceState에 문서 URI와 선언 키로 저장하고, Worker 요청 시 현재 분석 경로로 변환합니다. 미저장 문서는 세션에서만 보관합니다. 용어 변경은 이전 변경안을 무효화합니다. [지원 범위](TERMINOLOGY.md).

## 0.3 공개 준비 버전의 추가 구조

`src/core/scenarios.ts`는 최대 12개 입력을 현재 원본·대기 중인 Patch에 각각 넣어 전후를 비교합니다. 결과는 달라짐·같음·확인 불가·현재 결과로 구분합니다. 실패를 성공으로 취급하지 않으며, 객체 키 순서는 무시하되 undefined·NaN·-0 같은 값은 구별합니다. `scenarioModel.ts`는 UI용 타입·추천 입력·표시만 담당합니다. `report.ts`는 표시된 근거를 Markdown으로 만들며 자동 업로드하지 않습니다.

브라우저와 확장 기능은 `ScenarioLab.tsx`를 공유합니다. 웹은 Worker의 `compare` 요청, 확장은 Controller가 보관한 Patch ID와 문서 문맥을 검증한 뒤 Worker 요청을 사용합니다. UI가 적용 코드 전체를 호스트에 보내지 않습니다. 결과를 기다리는 중 파일·입력이 바뀌면 이전 결과를 버립니다.

`?demo=shipping`은 브라우저 저장소 복구와 쓰기를 모두 생략해 기존 프로젝트를 보존합니다. `lang=ko/en`으로 체험 언어를 지정합니다. 정적 호스팅의 하위 경로를 지원하도록 Vite base와 아이콘 경로는 상대 경로를 사용합니다.

버전별 배포는 `scripts/package-release.mjs`가 명시적인 소스 디렉터리 목록으로 구성합니다. 사용자 프로필·로그·비밀 설정·node_modules는 포함하지 않습니다. VSIX, 소스 ZIP, 미리 빌드한 체험 ZIP에 대한 SHA-256 체크섬을 생성합니다. GitHub 워크플로는 작성된 상태이며 실제 GitHub 실행 검증과 구분합니다.

## 현재 구조

```text
폴더/파일 선택 → 크기·확장자 필터 → 브라우저 작업 공간
                                   ↓
                          분석 전용 Web Worker
                                   ↓
                   TypeScript AST + 정확한 소스 범위
                                   ↓
         설명 / 함수 / 편집 규칙 / import 연결 / 검토 후보
                                   ↓
         이야기 카드 / 표 / 지도 / 코드 근거 / 점검 화면
                                   ↓
          직접 편집 또는 제한된 문장 요청 → 단일 Patch
                                   ↓
        구문 재검사 → 차이 보기 → 제한된 계산 비교 → 적용
                                   ↓
          바뀐 파일 재분석 / IndexedDB 저장 / ZIP 내보내기
```

화면은 React·TypeScript·Vite로 구성됩니다. `src/core`는 UI와 분리된 분석·수정·계산 엔진입니다. Worker가 큰 TypeScript 파서를 보유하고, UI는 직렬화 가능한 결과만 받습니다. 파서가 UI 번들에 중복 포함되지 않도록 `App.tsx`는 분석기나 수정기 자체를 import하지 않습니다.

## 핵심 파일

VS Code 확장 호스트·Worker·웹뷰·문서 버전 확인 구조는 [VS Code 구현 기록](VSCODE.md)에 정리했습니다. `extension/src`가 같은 `src/core`를 별도 Node Worker로 실행하고, VS Code 문서와 비교·편집·실행 취소 기능에 연결합니다.

| 파일                                   | 역할                                           |
| -------------------------------------- | ---------------------------------------------- |
| `src/core/analyze.ts`                  | AST 읽기, 설명, 위치, 규칙, 점검, 경로 연결    |
| `src/core/types.ts`                    | 언어 중립적인 설명·수정 데이터 모델            |
| `src/core/labels.ts`                   | 한국어·영어 용어와 비교 표현                   |
| `src/core/project.ts`                  | 변경된 파일만 재분석하는 캐시                  |
| `src/core/edit.ts`                     | 문장 요청 해석, 타입별 직렬화, 단일 범위 Patch |
| `src/core/simulate.ts`                 | 예산·깊이 제한이 있는 작은 AST 해석기          |
| `src/core/worker.ts` / `src/client.ts` | 작업 분리, 요청 식별, 오류·20초 시간 제한      |
| `src/core/import.ts`                   | 파일 필터, 상대 경로, 수량·크기 제한           |
| `src/storage.ts`                       | 현재 프로젝트의 로컬 저장                      |
| `src/components`                       | 이야기·지도·비교·연구·대화상자                 |
| `scripts/serve.mjs`                    | 로컬 루프백 전용 정적 빌드 서버                |

## 정확성을 위한 경계

- 코드의 문법 구조를 설명하는 계층과 도메인 의미 추론을 구분합니다. 이름 사전은 의미를 보장하지 않습니다.
- Patch에는 원본 전체와 정확한 위치·기존 텍스트를 넣습니다. 적용 직전에 원본이 달라졌으면 거부합니다.
- 입력 문자열은 JSON 문자열로 직렬화합니다. 숫자는 유한한 십진 표기만 허용합니다. 비교 연산은 허용 목록으로 제한합니다.
- 계산 미리보기는 업로드한 코드를 `eval`, `Function`, DOM, 네트워크, Node 프로세스에 전달하지 않습니다. 해석기에 없는 연산은 중단합니다.
- 전역 값 변경, 외부 모듈 초기화, 해석할 수 없는 초기화는 결과를 지어내지 않고 거부합니다.
- 문법 파싱 성공은 타입 검사나 실제 실행 테스트 성공과 다릅니다.
- 점검 항목은 확정된 버그가 아니라 근거와 한계가 있는 검토 후보입니다.
- 캐시는 원문 일치로 확인하고, 삭제된 파일은 제거합니다. 해시 충돌에 의존하지 않습니다.

## 최적화와 측정

분석 Worker는 UI와 별도 파일이며 ZIP 라이브러리는 내보내기 시 불러옵니다. 현재 버전의 번들 크기는 `pnpm build`와 `pnpm extension:build` 출력으로 확인합니다. CSS와 UI를 먼저 표시할 수 있지만 파서의 초기 로드 비용 자체가 사라지는 것은 아닙니다.

`pnpm bench`는 300개의 작은 합성 파일에 대해 최초 분석, 전체 캐시 적중, 한 파일 변경을 측정합니다. `docs/benchmark.json`에 환경·입력 크기·측정값을 저장합니다. 네트워크/Worker 전달/렌더링을 제외한 엔진 측정이므로 실사용 전체 지연으로 광고하지 않습니다.

## 다음 구현 순서

1. **용어 사전 확장:** 0.4의 파일/선언별 명칭을 실제 프로젝트에서 검증한 뒤 속성·import·중첩 선언과 공유 가능한 사전 형식을 검토합니다.
2. **실제 타입·테스트 근거:** TypeScript Language Service와 프로젝트 설정을 연결합니다. 실제 코드 실행은 별도 격리 프로세스에서 시간·메모리·파일·네트워크 권한을 제한합니다. 검증 결과에 실행 명령과 대상 버전을 기록합니다.
3. **언어 모델:** 0.7 개발판의 Ollama 어댑터를 언어·모델별 실제 사례로 검증합니다. 모델은 설명과 구조화된 편집안을 제안하고 원문·버전·검증기는 독립적으로 확인합니다. 입력 코드/주석 안의 명령을 지시로 실행하지 않습니다.
4. **Python과 다른 언어:** 언어별 파서 어댑터를 공통 `FileAnalysis` 모델에 연결합니다. 단순 줄별 번역이 아니라 이름 해석·제어 흐름·소스 위치를 유지합니다.
5. **의미 단위 변경:** 값 하나에서 시작해 조건 추가, 함수 추출, 여러 파일 변경을 트랜잭션으로 확장합니다. 의도·변경 범위·타입·테스트·되돌리기를 함께 묶습니다.
6. **큰 프로젝트:** Worker 요청의 변경분 전송, 분석 결과 분할 전달, 파일/표 가상화, 함수별 증분 AST 분석을 실제 대형 레포 측정 이후 적용합니다.
7. **비개발자 평가:** 별도 연구 문서의 정확성·오류 탐지·시간·과신 지표로 효과를 검증합니다.

시니어 개발자 수준에 가까워지려면 자연어 번역뿐 아니라 요구사항 정합성, 실패 설계, 데이터 모델, 권한, 회귀 테스트, 관측 가능성까지 근거와 함께 다뤄야 합니다. 현재 시제품은 그중 ‘이해→제한된 수정→비교’ 흐름의 실행 가능한 출발점입니다.
