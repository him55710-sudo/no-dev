# 구현 변경과 완료 기준 검토

구현이 끝나면 하단 `변경 검토`에서 실제 파일 diff와 검사 결과를 확인한다. `검토 크게 보기`로 공간을 넓힐 수 있다. 명령이 통과해도 완료 기준과 유지 조건을 자동으로 확인 완료 처리하지 않는다.

## 반영할 범위

작업을 시작할 때 구조 분석으로 수집한 `scopePaths`와 실제 변경 파일을 비교한다. 그 목록에 없던 파일은 `처음 수집한 범위 밖`으로 표시하며, 해당 파일의 반영 허용을 별도로 선택해야 원본에 반영한다. 새 테스트처럼 필요한 추가 변경도 이 목록에 들어갈 수 있다.

테스트·검사 설정 후보는 파일 경로로 분류한다. `test.js`, `*.test.ts`, `*.spec.tsx`, 테스트 폴더, 스냅샷, `package.json`, 주요 잠금·검사 설정, `scripts/`, GitHub Actions 파일 등이 대상이다. 표시된 파일의 diff에서 검사 내용·기대값·검사 대상의 변경을 확인하고 확인란을 선택한다. 추가·수정·삭제는 기존 변경 파일 목록에서도 구분한다.

이 표시는 테스트 약화 여부에 대한 의미 분석이 아니다. 이름만으로 모든 검사 도구나 사용자 정의 검증 파일을 찾을 수 없으므로 표시되지 않은 파일도 검토한다. `scopePaths` 역시 완전한 실행 영향 범위를 뜻하지 않는다. 에이전트는 이미 분리된 작업 복사본에서 추가 파일을 바꿨을 수 있으며, 이 확인은 **원본에 반영할 범위**를 통제한다. 파일별 실행 샌드박스나 외부 프로그램의 파일 접근 통제로 설명하지 않는다.

## 기준별 기록

완료 기준과 유지 조건마다 다음 중 하나를 선택한다.

- `아직 확인하지 않음`: 기본값. 검사 명령이 통과해도 이 상태를 유지한다.
- `사용자가 직접 확인`: 관찰한 결과와 근거를 반드시 적는다. 현재 작업에서 실제 통과한 검사 로그를 연결할 수 있다.
- `실패 확인`: 실패한 결과와 근거를 적는다. 실패·시간 초과·명령 없음 기록도 연결할 수 있다. 한 항목이라도 실패이면 반영할 수 없다.

검사 로그 연결은 사용자가 그 출력을 근거로 선택했다는 기록이다. 제품이 로그를 해석해 특정 기준의 충족을 증명한 것은 아니다. 확인 기록을 저장한 뒤 `검토한 변경 반영`을 누른다. 실패·시간 초과·실행하지 못한 검사 명령은 기존과 같이 반영을 막는다.

미확인 기준이 남아 있으면 확인하거나 `미확인 기준이 남아 있음을 알고 이번 변경을 반영합니다`를 명시적으로 선택한다. 이 선택은 기준을 확인 완료로 바꾸지 않는다. 반영 후에도 미확인 상태와 당시 기록을 보여준다. 알려진 실패를 이 선택으로 우회할 수는 없다.

## 저장과 유효성

검토 기록은 로컬 구현 작업 기록에 저장하며 작업 ID와 실제 변경 전체의 해시에 연결한다. 원본 코드나 설계를 저장하는 동작이 아니고 에이전트도 시작하지 않는다. 기록이 저장된 뒤에만 저장 완료 상태를 표시한다. 재시작 시 요청·변경 내용으로 파일 분류와 기준 목록을 다시 계산하며 저장된 UI 분류를 그대로 신뢰하지 않는다.

다른 작업의 기록, 오래된 변경안, 누락·중복 기준, 존재하지 않는 파일·검사, 중복된 검사 연결은 거절한다. 실패·시간 초과·명령 없음 기록은 실패·미확인 기준에 연결할 수 있지만 확인 완료의 근거로 사용할 수 없다. 기록 저장 직전에 실제 작업 복사본을 다시 확인하고, 반영 시 원본·작업 복사본 해시와 확정 설계를 다시 검사한다. 검토 전후 원본 파일 보호와 부분 반영 복구는 [AGENT_IMPLEMENTATION.md](AGENT_IMPLEMENTATION.md)의 기존 규칙을 유지한다.

자동 수정 전후의 검사 이력과 출력 생략 표시를 보존하는 동작은 [실패 검사·검토 기록](VERIFICATION_EVIDENCE.md)을 참고한다. 이전 회차의 통과를 현재 변경의 통과로 간주하지 않는다.

예전 버전의 작업 기록은 계속 읽지만 검토 기록 없이 새 반영을 진행할 수 없다. 이미 반영된 작업의 되돌리기와 복구에는 새 검토 입력을 요구하지 않는다. 검토 입력을 아직 저장하지 않은 상태에서 패널을 닫으면 그 입력은 복원되지 않는다. 여러 창의 검토 기록 자동 병합은 제공하지 않는다.

실제 모델 검증용 `pnpm agent:live-test`도 변경 검토 이후 표준 입력으로 명시적인 검토 기록을 받는다. 출력된 `decisionTemplate`을 실제 변경·검사 결과에 맞춰 작성하고 `{"action":"review","decision":...}` 형식으로 전달한다. 실행 승인 응답과 검토 기록은 서로 다른 동작이다.

## 확인한 범위

[회귀 검사](evidence/system-workspace/2026-10-16/review-validation.json)는 199개 테스트 통과를 기록한다. 검토 테스트는 범위 밖 파일과 테스트 변경 확인, 실제 검사 연결, 실패 차단, 작업·변경 해시 일치, 복원 및 변경안이 바뀐 후 반영 거절을 포함한다. Git 원본은 거절 시 그대로 남는지 확인한다.

[설치본 검사](evidence/system-workspace/2026-10-16/review-installed.json)는 실제 VSIX와 Production 모드에서 통과한 명령만으로 반영되지 않는지, 미확인 기준의 명시적 선택, VS Code 재시작 후 검토 기록 복원, 반영·undo·부분 반영 강제 종료 후 복구를 확인한다. 결정적인 테스트 응답기를 사용하며 외부 AI 품질의 증거가 아니다.

[화면 증거](evidence/system-workspace/2026-10-16/implementation-review.jpg)는 실제 React 컴포넌트와 브라우저 저장 모의 연결을 조작한 합성 자료다. 기준별 결과·근거·로그 연결, 새로고침 복원, 실패 시 버튼 차단, 반영 후 미확인 유지까지 확인했다. 설치본 Webview 전체를 마우스·키보드로 조작한 증거와는 구별한다.
