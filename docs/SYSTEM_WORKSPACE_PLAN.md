출처: 사용자가 이 구현의 기준으로 지정한 ‘기획 평가 분석’ 대화(2026-10-16). 아래는 마지막 기획 응답에서 접근 가능한 본문이다. 앞선 사용자 메시지의 구조 중심 탐색·점진적인 세부 설계·수정 후 구현 요구를 함께 확인했다. 과거 일부 응답과 첨부 Markdown은 대화 도구가 본문을 제공하지 않아 읽은 것으로 간주하지 않는다. 이 문서는 구현 완료 보고서가 아니다.

+**풀어봄은 ‘코드를 쉽게 설명하는 도구’가 아니라, ‘소프트웨어의 구조를 탐색하고 설계를 수정하면 에이전트가 실제 구현을 갱신하는 개발 플러그인’으로 만들자.**

네가 말한 **구조 중심의 화면, 선택할수록 깊어지는 세부 설계, 자연어 수정, 저장 후 에이전트 구현**을 제품의 중심으로 고정했어.

중요한 결정은 하나야. **첫 버전의 경험을 단순하게 줄이지 않는다. 대신 그 경험을 제대로 구현할 기술 환경을 좁힌다.**

# 풀어봄 최종 기획
### Pureobom — 소프트웨어를 이해하고 수정하는 설계 워크스페이스

## 1. 제품 정의와 고객

### 한 문장 정의

> **기존 코드베이스를 이해 가능한 시스템 구조로 보여주고, 사용자가 선택한 부분의 설계를 자연어로 수정하면 에이전트가 관련 코드와 테스트를 변경하는 오픈소스 개발 플러그인.**

사용자는 매번 새로운 프롬프트로 프로젝트를 설명하는 대신, **현재 소프트웨어와 연결된 설계 화면에서 원하는 부분을 직접 선택하고 수정**한다.

예를 들어 “우리 앱에 공유 기능을 추가해줘”라고 처음부터 설명하는 것이 아니라, 현재 프로젝트의 공유 시스템을 열고 권한 정책을 바꾸는 것이다.

제품의 핵심 흐름은 다음으로 고정한다.

**프로젝트 열기 → 구조 탐색 → 기능 선택 → 세부 설계 수정 → 저장하고 구현 → 변경 검토·반영 → 구조와 설명 갱신**

### 첫 고객

첫 고객은 **VS Code에서 AI로 앱을 만들고, 그 앱을 계속 고쳐 나가는 창업자·빌더**다. 제품이 어떻게 작동해야 하는지는 알지만, 생성된 코드 전체를 지속적으로 파악하기는 어려운 사람이다.

시니어 개발자에게는 같은 화면에서 더 깊은 정보를 제공한다. 코드를 숨기는 대신 **요구사항, 구현 위치, 변경 영향, 검증 결과를 연결하여 검토할 수 있게** 한다.

비개발자용 제품과 개발자용 제품을 따로 만드는 것이 아니라, **같은 시스템을 서로 다른 깊이로 탐색하는 제품**으로 설계한다.

### 차별점은 정확하게 잡아야 한다

요구사항을 작성하고 설계·작업·구현으로 연결하는 흐름은 이미 Kiro와 GitHub Spec Kit에도 있다. 따라서 “PRD를 수정하면 AI가 구현한다”만으로 새로운 제품이라고 주장하면 약하다. 

풀어봄이 집중할 차별점은 다음 경험이다.

> **이미 존재하는 소프트웨어의 구조를 보고, 그 구조에 연결된 설계를 수정하고, 실제 구현과의 대응 관계를 계속 유지한다.**

즉, 문서 작성 도구도 아니고 아키텍처 그림 생성기도 아니다. **구조·설계·코드·검증을 연결하는 편집 환경**이다.

## 2. 인터페이스: 코드를 ‘파일’보다 ‘시스템’으로 먼저 보여준다

### 첫 화면은 채팅창이 아니라 시스템 워크스페이스

VS Code 안에 전용 에디터 탭으로 연다. 별도의 IDE를 만들지 않고, 사용자가 작업하던 프로젝트 안에서 바로 접근하게 한다.

| 화면 영역 | 보여주는 내용 | 핵심 역할 |
|---|---|---|
| 상단 | 프로젝트, 현재 탐색 경로, 검색, 분석 상태, `저장하고 구현` | 지금 어느 부분을 보고 수정하는지 유지 |
| 왼쪽 | 시스템·기능 탐색 트리 | 전체 구조에서 원하는 부분을 찾기 |
| 중앙 | 선택한 수준의 구조와 연결 관계 | 무엇이 무엇에 의존하는지 이해 |
| 오른쪽 | 선택한 대상의 세부 설계 | 읽기·수정·근거 확인 |
| 하단 | 현재 변경 작업의 진행과 검증 결과 | 에이전트가 무엇을 하고 있는지 확인 |

**중앙 캔버스와 오른쪽 설계 패널이 주인공**이다. 채팅은 특정 부분에 질문하거나 요구사항을 구체화할 때만 사용하는 보조 기능으로 둔다.

VS Code의 Webview는 이런 사용자 정의 화면을 구현할 수 있다. 다만 코드 열기, diff, 진단, 설정까지 전부 새로 만들지 않고 편집기의 기본 기능을 재사용한다. 

### 선택할수록 깊어지는 네 계층

| 깊이 | 사용자가 알고 싶은 것 | 예시 |
|---|---|---|
| **시스템** | 이 앱은 무엇으로 이루어져 있나? | 사용자 관리, 프로젝트 관리, 공유, 저장 |
| **기능·흐름** | 이 부분은 어떻게 연결되어 작동하나? | 공유 화면 → API → 권한 검사 → 데이터 |
| **규칙·상태** | 어떤 조건에 따라 동작이 달라지나? | 소유자는 편집 가능, 읽기 전용 멤버는 조회만 가능 |
| **구현·증거** | 실제 어디에 구현되어 있고 무엇을 확인했나? | 함수, 관련 파일, 테스트, 실행 결과 |

서로 다른 추상화 수준으로 확대하는 방식은 C4 모델의 계층적 접근을 참고할 수 있다. 다만 풀어봄에서는 정해진 다이어그램 형식을 그대로 따르기보다 **사용자가 수정하려는 과제에 맞게 계층을 구성**한다. 

### 실제 조작 방식

시스템을 한 번 선택하면 오른쪽에 역할과 핵심 정책이 나타난다. 하위 구조를 열면 중앙 화면이 해당 시스템 내부로 들어간다. 규칙을 선택하면 조건·예외·데이터·검증 기준이 펼쳐진다. 근거를 선택하면 실제 코드로 이동한다.

**연결선도 선택할 수 있어야 한다.** 예를 들어 “공유 API → 권한 검사”를 선택하면 어떤 정보를 전달하는지, 언제 호출하는지, 실패하면 어떻게 처리하는지 보여준다.

반대 방향도 필요하다. 개발자가 코드를 보고 있을 때 `풀어봄에서 보기`를 실행하면 해당 코드와 연결된 기능·규칙이 강조되어야 한다.

### 현대적인 화면을 만드는 기준

현대적이라는 것을 어두운 배경, 형광색, 움직이는 선으로 해결하지 않는다.

**처음에는 핵심 구조만 보이고, 관심 있는 부분이 자연스럽게 확대되며, 사용자가 보고 있던 위치가 유지되는 것**을 우선한다. 상태는 색상뿐 아니라 문구와 아이콘으로 구분하고, 오른쪽 문서가 길어지면 집중 보기로 확장한다.

전체 코드베이스의 노드 수백 개를 한 번에 펼쳐 놓는 화면은 피한다. 캔버스가 불편한 사용자는 왼쪽 트리와 검색만으로도 같은 정보에 접근할 수 있게 한다.

또한 중요한 구분이 있다.

**노드를 움직이는 것은 화면 배치이고, 시스템을 변경하는 것은 설계 편집이다.**  
그림을 정리했는데 코드 구조까지 바뀌어서는 안 된다.

## 3. 선택하면 나타나는 문서: Living Spec

네가 말한 “PRD 같은 세부사항”을 제품에서는 **Living Spec, 즉 코드와 연결된 살아 있는 설계 명세**로 정의하자.

단, 모든 기능에 긴 PRD를 하나씩 붙이는 방식은 아니다. 선택한 수준에 맞는 정보만 보여준다.

### 세부 설계에 들어갈 내용

| 항목 | 설명 |
|---|---|
| **역할과 목적** | 이 부분이 무엇을 담당하는지 |
| **현재 구현** | 현재 코드에서 확인할 수 있는 동작 |
| **원하는 동작** | 사용자가 구현시키려는 요구사항 |
| **정책과 조건** | 권한, 분기, 상태 변화, 제한 |
| **입출력과 데이터** | 무엇을 받고, 반환하고, 저장하는지 |
| **예외와 실패 처리** | 실패했을 때 어떻게 되는지 |
| **유지해야 하는 동작** | 이번 수정으로 깨뜨리면 안 되는 것 |
| **완료 기준** | 어떤 사례를 확인해야 변경이 끝난 것인지 |
| **구현 근거** | 연결된 코드, 테스트, 변경 기록 |

상위 시스템에서는 역할과 경계를 먼저 보여주고, 세부 규칙에서는 조건과 결과를 먼저 보여준다. 시니어 개발자는 더 내려가 인터페이스 계약, 구현 제약, 오류 처리까지 확인한다.

### 자연어를 직접 수정하되, 현재 사실은 보존한다

화면에 다음 문장이 있다고 하자.

> 프로젝트에 참여한 멤버는 프로젝트를 수정할 수 있습니다.

사용자는 그 자리에서 다음처럼 바꾼다.

> 읽기 전용 멤버는 조회만 할 수 있습니다. 소유자와 편집 권한이 있는 멤버만 수정할 수 있습니다.

사용 경험은 문장을 직접 고치는 것이지만, 내부에서는 원래 설명을 삭제하지 않는다.

**기존 문장은 현재 구현의 기준선으로 남고, 수정한 문장은 구현할 목표가 된다.** 사용자는 같은 패널에서 변경 전후를 확인할 수 있다.

이렇게 해야 “문서를 고쳤으니 이미 구현됐다”는 착각을 막을 수 있다.

### 문구 수정과 동작 변경은 구분한다

“사용자”를 “회원”으로 바꾸거나 설명을 읽기 좋게 다듬는 것은 코드 수정 요청이 아닐 수 있다.

따라서 편집에는 두 가지 의미를 둔다.

**설명 다듬기**는 문서·용어만 갱신한다.  
**동작 변경**은 에이전트 구현 작업을 만든다.

매번 복잡한 모드를 선택하게 하지는 않되, 제품이 두 작업을 구분하고 모호한 경우에만 확인해야 한다.

그리고 **코드만 보고 ‘왜 이렇게 만들었는지’를 사실처럼 복원하지 않는다.** 코드에서 확인한 동작과 개발자의 원래 의도는 다르다. 의도는 기존 문서나 사용자가 제공한 정보에서 가져오고, 근거가 없으면 추정 또는 미확인으로 남긴다.

## 4. 대표 경험: ‘읽기 전용 공유 권한’ 추가

첫 데모는 무료배송 기준이나 버튼 문구 변경보다 깊어야 한다.

내가 선정한 대표 과제는 **기존 프로젝트의 공유 권한을 바꾸는 것**이다. 화면, API, 권한 로직, 테스트가 함께 바뀌므로 네가 구상한 시스템 중심 편집을 보여주기 좋다.

### 사용자가 하는 일

프로젝트를 열고 **프로젝트 관리 → 공유·권한**으로 들어간다.

현재 구조와 규칙을 확인한 뒤 다음 요구사항을 저장한다.

> 읽기 전용 멤버는 프로젝트를 볼 수 있지만 수정할 수 없다. 소유자와 편집 권한이 있는 멤버는 기존처럼 수정할 수 있다. 화면에서 편집을 막는 것뿐 아니라, 수정 요청도 서버에서 거절해야 한다.

### 풀어봄이 하는 일

해당 요구사항과 연결된 편집 화면, API, 권한 검사, 관련 테스트를 찾고 구조도에서 강조한다.

이후 에이전트가 각 부분을 수정한다. 사용자가 파일명을 일일이 찾거나 “백엔드도 바꿔줘”라고 추가로 반복 요청하지 않아도 되도록 설계한다. 다만 관련 부분을 찾지 못했거나 지원하지 않는 구조라면 그 공백을 표시한다.

완료 기준은 다음처럼 확인 가능한 동작으로 제시한다.

| 확인 사례 | 기대 결과 |
|---|---|
| 읽기 전용 멤버가 프로젝트 조회 | 정상 조회 |
| 읽기 전용 멤버가 편집 화면 접근 | 편집 불가 표시 |
| 읽기 전용 멤버가 수정 API 직접 호출 | 수정 거절, 데이터 변경 없음 |
| 편집 권한 멤버가 정상 수정 | 기존 기능 유지 |
| 소유자가 정상 수정 | 기존 기능 유지 |
| 다른 프로젝트의 권한을 이용해 수정 시도 | 해당 프로젝트의 권한에 따라 거절 |

반영 후에는 구조와 설명이 갱신되고, 각 기준을 무엇으로 확인했는지 연결되어야 한다.

**이 정도 경험이 완성되어야 ‘새로운 개발 인터페이스’라는 주장을 할 수 있다.**

첫 검증 프로젝트는 이미 멤버·역할 데이터와 테스트 환경이 있는 앱을 선택한다. 데이터 구조가 없는 다른 프로젝트까지 동일하게 처리된다고 주장하지 않는다. 권한 변경은 검토가 필요한 작업으로 취급하고, 데모는 테스트용 환경에서 수행한다.

---

## 5. 저장하면 에이전트가 구현한다

네가 원하는 자동화는 유지한다. **사용자가 설계를 저장했는데 다시 채팅창에서 “이대로 구현해줘”라고 말하게 만들면 안 된다.**

### 기본 실행 흐름

**설계 저장 → 의미 변경 확인 → 관련 코드 수집 → 변경 계획 → 분리된 작업 공간에서 구현 → 검사와 오류 수정 → 검토·반영 → 재분석**

최초 연결에서 프로젝트별 허용 범위와 실행 정책을 설정한다. 이후 `저장하고 구현`을 누르면 허용된 범위 안에서는 에이전트가 계속 진행한다.

일반적인 자동 초안 저장은 실행을 시작하지 않는다. 모델이 설명을 갱신하거나 번역한 것도 다시 구현을 시작하지 않는다. 그래야 저장과 갱신이 서로를 반복 호출하는 문제가 생기지 않는다.

### 에이전트는 ‘바뀐 문장’만 받는 것이 아니다

내부적으로는 다음 맥락을 묶어서 전달해야 한다.

**어느 기능을 바꾸는지, 기존 동작과 새 동작의 차이가 무엇인지, 어떤 동작을 유지해야 하는지, 어떤 파일을 수정할 수 있는지, 무엇을 검사해야 하는지.**

이 묶음을 **변경 명세**로 관리한다.

핵심은 “PRD 전체를 프롬프트로 보내기”가 아니다. **변경된 의미와 관련 맥락을 정확히 전달하는 것**이다.

### 자동화하되 원본 작업은 보호한다

기본 모드에서는 에이전트가 분리된 작업 공간에서 코드를 수정한다. 사용자는 결과와 검증 내용을 보고 현재 프로젝트에 반영한다.

사전에 허용한 범위 안의 구현과 검사는 자동으로 진행하지만, 운영 배포, 데이터 마이그레이션, 새로운 비용 발생, 비밀 정보 접근, 작업 범위를 벗어난 수정은 별도 권한이 필요하다.

작업 도중 사용자가 원본 코드를 수정하면 기존 결과를 그대로 덮어쓰지 않는다. 기준이 바뀌었다고 표시하고 재검증하거나 변경안을 다시 만든다.

### ‘최적화’는 이렇게 정의하자

기본 자동 작업에는 **요구사항 반영, 그로 인해 생긴 타입·연결 오류 수정, 필요한 테스트 보완, 일관성 정리**를 포함한다.

반면 속도나 메모리를 개선하는 성능 최적화는 별도 목표로 다룬다. 무엇을 개선할지 정하고 전후를 측정해야 한다. 기존 저장소의 개발 계획도 더 느려진 최적화 제안을 채택하지 않았다고 기록하고 있다. 이런 원칙은 유지할 가치가 있다. 

**저장할 때마다 프로젝트 전체를 재작성하는 것이 아니라, 변경된 설계를 충족하도록 필요한 부분을 고치고 검증하는 자동화**다.

## 6. 가장 중요한 기반: 코드와 설계를 계속 연결한다

화려한 화면보다 이 부분이 핵심이다.

### 전체 코드를 다루되, 줄별 번역에 갇히지 않는다

장기 목표는 프로젝트 전체에서 자연어와 구조를 통해 구현까지 접근할 수 있게 하는 것이다.

다만 코드 1,000줄을 자연어 1,000문장으로 바꾸지는 않는다. 조건·함수·상태·데이터·기능으로 묶는다. 지원하지 않거나 묶지 못한 코드는 숨기지 않고 **미분류·미지원 영역으로 원본 탐색 경로를 유지**한다.

또한 기능과 파일을 일대일로 연결하지 않는다. 하나의 기능이 여러 파일에 걸칠 수 있고, 하나의 함수가 여러 기능에 사용될 수 있기 때문이다.

### 연결은 줄 번호만으로 만들지 않는다

파일, 심볼, 소스 범위, 분석 시점의 버전 등을 함께 보존한다. 이름 변경이나 코드 이동이 발생하면 재연결하고, 확실하지 않으면 재연결이 필요하다고 표시한다.

자연어 문장에 소스 링크를 붙였다는 이유만으로 설명이 정확해지는 것도 아니다. **코드 근거가 있다는 것과 해석이 옳다는 것은 별도로 검토해야 한다.**

### 코드가 바뀌었다고 사용자의 목표를 바꾸지 않는다

이것은 반드시 지켜야 할 규칙이다.

사용자의 설계가 “읽기 전용 멤버는 수정할 수 없다”인데, 다른 에이전트가 코드를 잘못 바꿔 수정 가능해졌다고 하자.

풀어봄이 설명을 다음처럼 갱신해버리면 안 된다.

> 읽기 전용 멤버도 수정할 수 있습니다.

관측된 현재 동작의 설명은 갱신할 수 있지만, **사용자가 확정한 목표는 유지하고 불일치를 표시해야 한다.**

화면에는 다음처럼 보여주는 것이 맞다.

> **설계와 구현의 재검토가 필요합니다.**  
> 목표: 읽기 전용 멤버의 수정 차단  
> 발견 사항: 수정 경로에서 권한 검사가 확인되지 않음

단, 정적 분석만으로 실제 동작을 단정할 수 없는 경우에는 “확인되지 않음”과 “실제로 허용됨”을 구분한다.

### 신뢰도 점수 대신 검증 범위를 보여준다

“안전성 96점” 같은 숫자는 넣지 않는다.

대신 **수행한 검사, 통과한 사례, 실패한 사례, 실행하지 못한 검사, 아직 확인하지 못한 영향**을 보여준다.

풀어봄의 목표는 AI에 대한 무조건적인 신뢰를 높이는 것이 아니라, **무엇을 믿어도 되고 무엇을 더 확인해야 하는지 판단하게 하는 것**이다.

## 7. 첫 제품 범위: 경험은 깊게, 지원 환경은 좁게

첫 검증 환경은 **데스크톱 VS Code의 로컬 Git 프로젝트와 TypeScript·React·검증한 Next.js 구성**으로 잡는다.

여기서 줄이는 것은 제품의 깊이가 아니라 환경의 다양성이다.

### 첫 버전에 반드시 들어갈 것

| 핵심 기능 | 완료 기준 |
|---|---|
| 실제 프로젝트 구조 분석 | 준비된 그림이 아니라 실제 코드와 연결됨 |
| 계층적 구조 탐색 | 시스템에서 규칙·코드까지 내려갈 수 있음 |
| Living Spec 편집 | 현재 동작과 목표 변경을 구분함 |
| 다중 파일 변경 | UI·API·로직 등 관련 부분을 하나의 작업으로 수정함 |
| 실제 검사와 검토 | 변경 근거, 검사 결과, 미확인 범위를 제시함 |
| 반영·복구·동기화 | 사용자 변경을 보호하고 설계와 코드의 대응을 갱신함 |

반대로 독립 IDE, 모든 언어 지원, 운영 DB 자동 마이그레이션, 자동 배포, 무제한 자가 최적화, 대규모 실시간 공동편집은 첫 범위에서 제외한다.

**“모든 언어를 조금씩 설명하는 제품”보다 “한 환경에서 실제 기능을 끝까지 수정하는 제품”을 먼저 만든다.**

기존 구조를 자유롭게 재배선하거나 전체 프로젝트를 리팩터링하는 기능은 이후 확장한다. 첫 버전은 이미 있는 구조에서 사용자가 원하는 의미 있는 변경을 완성하는 데 집중한다.

## 8. 구현 방향: 기존 기반은 살리고 핵심 모델을 확장한다

현재 저장소의 설계 문서에는 TypeScript AST·Worker 분석, 소스 위치 보존, 제한된 계산 비교, 변경 감지, diff·적용·undo, 개발판의 로컬 Ollama 연결이 기술되어 있다. 이 기반을 버리고 처음부터 만들 필요는 없다. 다만 이번 검토는 문서 확인이며, 전체 코드를 실행해 검증한 것은 아니다. 

새로 필요한 중심 요소는 다음이다.

| 구성 요소 | 맡는 역할 |
|---|---|
| **구조 분석기** | 코드·심볼·지원되는 관계를 추출 |
| **시스템 모델** | 기능과 코드의 대응, 사용자 명칭과 묶음을 유지 |
| **설계 엔진** | 현재 구현·목표·유지 조건·완료 기준을 관리 |
| **변경 관리자** | 의미 차이, 작업 범위, 버전, 실행 상태를 관리 |
| **에이전트 어댑터** | 선택한 모델·에이전트에 작업을 전달 |
| **검증·반영 계층** | 검사, 결과 기록, 충돌 확인, 반영과 복구 수행 |

### 새로운 코딩 에이전트를 전부 직접 만들지는 않는다

제품의 핵심 자산은 코딩 모델이 아니라 **시스템과 설계를 코드에 정확히 연결하는 구조**다.

기존 Ollama 경로를 유지하되, Ollama 자체를 완성된 프로젝트 수정 에이전트로 취급해서는 안 된다. 문맥 수집, 변경 범위 확인, 실행 권한, 검증은 별도로 구현해야 한다.

외부 에이전트는 하나만 먼저 통합한다. 첫 후보로는 인증·승인·진행 이벤트를 자체 제품과 연결하도록 문서화된 Codex App Server를 검토할 수 있다. 다만 공식 문서의 실험적 인터페이스 주의를 반영해 버전을 고정하고 실제 연동을 검증한 뒤 지원한다고 표시해야 한다. 

모든 에이전트가 똑같이 동작한다고 가정하지 않는다. 취소, 다중 파일 수정, 승인 요청, 검사 실행 등 지원 능력을 따로 관리한다.

### 로컬과 실행 권한

기본 분석은 로컬에서 수행하고 외부 모델 전송은 명시적으로 선택하게 한다. 로컬 모델은 유료 API 키가 필요하지 않지만 컴퓨터 자원과 실행 비용은 남는다.

비신뢰 저장소에서는 정적 탐색만 허용하고 실행 기능은 제한한다. VS Code도 Workspace Trust를 통해 의도하지 않은 코드 실행을 제한하는 구조를 제공한다. 

또한 **Git worktree로 작업을 분리하는 것과 실행을 보안상 격리하는 것은 다른 문제**다. 이 둘을 혼동해 “안전한 샌드박스”라고 홍보하면 안 된다.

## 9. 개발 순서와 완성 기준

날짜보다 실제 작동 증거로 단계를 나누자.

| 단계 | 만들어야 할 결과 | 통과 기준 |
|---|---|---|
| **1. 구조 모델** | 기능·코드·관계·버전의 연결 | 실제 프로젝트에서 노드와 소스를 왕복 탐색 |
| **2. 탐색 화면** | 캔버스·트리·세부 설계 패널 | 사용자가 원하는 규칙과 근거까지 도달 |
| **3. 설계 편집** | 의미 변경·유지 조건·완료 기준 | 문구 수정과 동작 변경을 구분 |
| **4. 구현 연결** | 에이전트·다중 파일 변경·검사 | 대표 공유 권한 변경을 끝까지 완료 |
| **5. 동기화·복구** | 외부 변경 감지·불일치·복구 | 오래된 결과로 사용자 작업을 덮어쓰지 않음 |
| **6. 공개 품질** | 설치 패키지·실제 데모·지원 표 | 예제 밖 프로젝트에서도 성공·실패를 재현 |

화면은 임시 데이터로 제작을 시작할 수 있지만, 두 번째 단계가 끝날 때는 실제 분석 결과에 연결되어야 한다.

### 특히 먼저 확인할 실패 상황

에이전트 실행 중 사용자가 코드를 수정한 경우, 취소한 뒤 결과가 늦게 도착한 경우, 일부 파일만 반영된 경우, 검사 도구가 없는 경우, 자동 설명 갱신이 다시 구현을 시작하는 경우를 검증해야 한다.

이런 실패를 처리하지 못하면 성공 데모가 좋아도 실사용 제품으로 보기 어렵다.

### 사용자 검증은 두 가지를 따로 본다

**기술적으로 요구사항을 구현했는가**와 **사용자가 더 정확하게 판단하게 되었는가**는 다른 문제다.

초기에는 비개발 빌더와 숙련 개발자를 나누어, 기존 에이전트만 사용하는 조건과 풀어봄을 함께 사용하는 조건을 비교하자. 볼 것은 수정 위치 탐색 시간, 영향 설명의 정확성, 잘못된 변경 승인, 도움 요청, 실제 프로젝트 재사용이다.

소규모 관찰 결과를 시장 전체의 효과로 일반화하지 않는다. 동시에 사용자 모집이 늦어진다는 이유로 독립적인 구현·검증 작업을 멈출 필요도 없다.

## 10. 오픈소스 공개 전략

### 공개할 핵심

**구조 모델, 코드–설계 연결, Living Spec 편집, 변경·검증 연결, 에이전트 어댑터 계약**을 공개하는 방향으로 간다.

단순히 무료 UI만 공개하고 중요한 연결 부분을 감추면, 이 제품이 강조하는 검토 가능성과 맞지 않는다.

처음부터 회원가입이나 결제로 핵심 체험을 막지 않는다. 모델이 없어도 구조를 읽고 원본 근거를 살펴볼 수 있게 하고, 쓰기 기능은 검증된 실행 환경을 연결했을 때 제공한다.

### 첫 공개에서 보여줘야 할 장면

짧은 데모에는 다음 경험이 들어가야 한다.

**실제 앱의 구조를 선택한다 → 권한 설계를 수정한다 → 관련 시스템이 강조된다 → 여러 파일과 테스트가 바뀐다 → 결과를 반영하면 구조와 설명이 갱신된다.**

상세 데모에는 실패도 하나 보여주자. 예를 들어 화면만 바뀌고 서버 권한 검사가 빠져 테스트가 실패하는 장면이다.

사용자가 봐야 하는 것은 “AI가 또 코드를 만들었다”가 아니라 다음이다.

> **“내 소프트웨어의 어느 부분을 바꾸는지 이해하면서, 구현과 검증까지 연결할 수 있구나.”**

### 스타보다 먼저 볼 지표

초기 핵심 지표는 **자기 프로젝트에서 설계 변경을 완료한 사람과, 다음 변경 때 다시 사용한 사람**이다.

스타는 관심의 지표로 보되 재사용의 증거로 취급하지 않는다. 기여도 역시 번역 파일 개수보다 실제 실패 사례, 구조 분석 개선, 에이전트 연동, 검증 예제가 중요하다.

팀 승인 정책이나 조직 차원의 설계·코드 불일치 관리 등은 후속 수익화 후보가 될 수 있다. 하지만 지금부터 함께 만들지는 않는다. 첫 번째 완전한 편집 경험을 먼저 증명해야 한다.

## 최종적으로 지켜야 할 제품의 중심

풀어봄을 다음 세 가지 중 하나로 축소하면 안 된다.

**코드보다 긴 설명문을 만들어주는 도구.**  
**예쁜 시스템 그림만 보여주는 도구.**  
**PRD를 저장한 뒤 다시 채팅으로 구현을 부탁해야 하는 도구.**

최종 제품은 다음이어야 한다.

> **풀어봄은 소프트웨어를 시스템 구조로 이해하고, 선택한 부분의 설계를 자연어로 수정하면, 에이전트가 관련 코드를 변경·검사하고 설계와 구현의 연결을 갱신하는 오픈소스 개발 플러그인이다.**

소개 문장은 이것으로 잡겠어.

### **“코드를 시스템으로 이해하고, 설계를 바꾸면 구현이 바뀝니다.”**

개발 순서도 명확해. **실제 코드와 연결된 구조 모델 → 선택 가능한 설계 화면 → 의미 변경 명세 → 다중 파일 구현·검증 → 동기화**다. 디자인만 먼저 완성하거나 지원 언어부터 늘리는 방향으로 새지 않게 해야 한다.
