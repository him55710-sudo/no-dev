# 완료 응답과 취소가 겹치는 경우

2026-10-20. 원래 기획의 ‘취소 뒤 늦게 도착한 결과를 무효화한다’는 조건을
검토하면서 에이전트 연결 계층의 경합을 재현했다.

`turn/completed`를 처리하면 완료 Promise가 먼저 해결된다. 같은 이벤트를
처리하는 동안 취소 신호가 들어오면, 이미 해결된 Promise에 대한 `reject`는
결과를 바꾸지 않는다. 기존 `run()`은 기다리기 전에만 취소 여부를 확인해서
취소된 실행을 `completed`로 반환했다.

`CodexAppServer.run()`이 완료 결과를 받은 직후에도 취소 신호를 확인하도록
수정했다. 정상 완료·실패·승인 대기·시간 제한과 프로세스 종료 경로는 유지한다.
상위 작업 관리자는 기존에도 `server.run()` 뒤에 취소를 확인했다. 이번 재현은
연결 계층의 잘못된 성공 반환이며, 취소된 코드가 원본에 반영됐다는 관측은 아니다.

## 재현과 검증

실제 자식 프로세스로 실행하는 결정적 프로토콜 시험 서버에 명시적 완료 명령을
추가했다. 실행 세션이 열린 뒤 명령을 보내고, 내부 완료 처리 다음의 이벤트
구독자에서 취소한다. 완료 응답을 실제로 받았고 호출자에게 결과가 전달되기 전에
취소했는지를 각각 검사한다. 시간 지연에 의존해 우연히 경합시키지 않는다.

- 수정 전: 새 검사 1개 실패, 선택하지 않은 기존 검사 11개 생략. 예상한 거절
  대신 `resolved`가 반환되는 것을 확인했다.
- 수정 후: 프로토콜 검사 12개 통과, 생략 0개. 새 경합 검사와 기존 정상 완료,
  실패, 승인 대기, 취소, 실행 시간 제한이 포함된다.
- 관련 검사: 관리 호스트·작업 복구·검사 실행·실패 이력·분리 작업 공간의
  5개 파일, 33개 검사 통과. 원본 변경 충돌, 부분 반영 복구, 중단된 작업의
  새 세션 이어하기와 실제 자식 프로세스 종료를 포함한다.
- 확장 타입 검사·번들 빌드·VSIX 패키징 통과.
- 새 VSIX `ae60ff55f5207c5e01aede5f6be8c7bb341cd6b78ccb9e9448b3d2c048e89c6f`를
  실제 VS Code에 설치해 여섯 독립 실행의 검토 복원·반영·undo·중간 종료 복구를
  통과했다. 원본 여섯 파일과 staged/unstaged 변경·Git HEAD/index를 보존했다.
  이는 설치 호스트의 회귀 검사이며 위 경합을 네이티브 포인터로 재현한 것은 아니다.
- 릴리스 체크섬·소스 manifest·포함된 라이선스·VSIX와 저장소 밖에서 추출한
  분석/언어 도구 검사를 통과했다. 소스 ZIP에는 이번 변경 파일도 포함한다.

[실행별 근거](evidence/terminal-cancellation.json)에서 수정 전 실패와 수정 후
통과를 구분한다. 시험 서버는 외부 AI가 아니며, 네이티브 포인터 조작이나
사람의 사용성 결과를 이 검사로 대신하지 않는다.

직전 UI 커밋 `436b40f`의 [Windows·Ubuntu CI](https://github.com/him55710-sudo/no-dev/actions/runs/39349428048)는
모두 성공했다. [최종 상태 기록](evidence/progressive-spec/final-ci.json)은 그 커밋의
검사·패키징 결과이며 이번 취소 수정의 CI 결과와 구분한다.

## 후속: 같은 수신 묶음에 남은 응답

첫 수정 뒤 수신 버퍼도 확인했다. 기존 수신기는 묶음 처리를 시작할 때만
연결 종료를 확인했다. 첫 프레임의 구독자가 취소하면 연결은 닫혔지만,
같은 묶음에 남은 파일 승인 요청·진행 메시지·완료 프레임은 계속 전달됐다.
종료 과정에서 비운 승인 목록에도 새 요청이 다시 들어갔다.

각 프레임을 꺼내기 전에 연결 종료 상태를 확인하도록 바꿨다. 종료 이후에는
남은 승인 요청과 진행·완료 알림을 전달하지 않는다. 기존 정상 응답 처리와
승인 대기 동작은 유지한다. 상위 작업 관리자의 승인 콜백도 이미 취소 신호를
확인하므로, 이번 결과를 취소된 명령이 실제 실행됐다는 관측으로 확대하지 않는다.

새 검사는 실제 시험 프로세스의 세션을 연 뒤, 취소 알림·파일 승인·진행 알림·완료를
하나의 버퍼로 수신 메서드에 직접 전달한다. 운영체제가 표준 출력 묶음을 쪼개
문제를 우연히 가리는 것을 피하기 위한 단위 검사다. 외부 에이전트가 이 순서의
응답을 실제로 보냈다고 설명하지 않는다.

[후속 실행 기록](evidence/buffered-cancellation.json): 수정 전 새 검사 1개 실패·12개
생략에서 늦은 승인 ID `20`이 콜백에 전달됐다. 수정 후 프로토콜 13개와 관리
호스트 8개, 총 21개 검사가 통과했다. 취소로 실행이 거절되고 늦은 승인·이벤트가
전달되지 않으며, 그 승인 ID를 나중에 수락할 수도 없음을 확인했다.

타입 검사·번들 빌드·패키징을 통과한 새 VSIX
`1e900e849fc5bed4d7ddb66629f8697a0a335b3a2b12fc03b3f4f4e75b458ba0`의
여섯 독립 설치 실행에서도 검토 복원·반영·undo·중간 종료 복구를 통과했다.
원본 여섯 파일·staged/unstaged 변경·HEAD/index를 보존했다. 이 설치 회귀는
버퍼 경합을 네이티브 마우스 조작으로 재현한 검사와는 구분한다.
