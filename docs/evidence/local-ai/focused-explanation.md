# 함수 단위 설명 선택과 실제 프로젝트 후속 평가

2026-10-20 KST, 0.7 개발 소스의 기록이다. 공개 안정판/Pages 0.6.0을 배포한 기록이 아니다. [사용 방법·검증 경계](../../FOCUSED_EXPLANATIONS.md).

## 실제 사용자 프로젝트

앞선 가독성 요청에서 서식 부분은 별도 포매터와 원래 테스트 8→8→8·복구로 확인했다. 이번에는 같은 원문을 변경하지 않고 함수의 역할·입력 전제 설명 부분을 요청했다. 비공개 원문·프로젝트명·경로·함수명·원시 요청/응답은 공개하지 않는다. 전체 자료는 로컬 평가 폴더에 보존한다.

| 시도                                   | 실제 결과                                                                                      | 판정                                                   |
| -------------------------------------- | ---------------------------------------------------------------------------------------------- | ------------------------------------------------------ |
| 3B 모델 연결 확인                      | 선택한 모델이 해당 서버에 없어 코드 전송 전 거절                                               | 설명 생성 아님                                         |
| 설치된 4B 모델, 함수 선택 필드 추가 전 | cloud-disabled 로컬 서버, 실제 제품 클라이언트, 180초 시간 초과                                | 완성 응답 없음, 의미 정확성 미평가                     |
| 함수 선택 평가 도구 준비               | 분석기를 단독 번들한 평가 도구에서 의존 모듈 해석 실패                                         | 모델 실행 전 준비 실패; 제품 모델 실패로 합산하지 않음 |
| 3B 모델, 함수 선택 필드 추가 후        | 실제 제품 클라이언트와 빌드 worker로 범위 확인, 별도 cloud-disabled 로컬 서버, 180초 시간 초과 | 완성 응답 없음, 의미 정확성 미평가                     |

평가 도구는 분석기를 임의로 번들하는 대신 제품의 실제 빌드 worker를 사용하도록 수정했다. 두 실제 생성 요청은 모델·서버·기능 상태가 다르므로 속도·정확도 비교 실험이 아니다. 시간 제한을 늘리거나 실패를 성공으로 바꾸지 않았다. 우리 검증용 Ollama만 종료했고 사용 중이던 다른 로컬 서버는 변경하지 않았다. 변경안을 적용하거나 사용자 원래 작업 폴더를 수정하지 않았다.

평가자가 정한 경계 입력 7개를 **변경하지 않은 실제 함수**에 실행해 검토 기준을 마련했다. 이는 원래 프로젝트 테스트 8개와 별개이며, 모든 호출 전제·실제 결함·과학적 모델 타당성이나 모델 설명 정확성을 입증하지 않는다. 실제 답변이 없어 기준에 대한 채점은 하지 않았다. 민감한 구체 입력과 결과는 로컬 보고서에만 남겼다.

## 제품 검사

- 핵심 로컬 AI 검사 14개 통과. Unicode/CRLF 함수 범위, 전체 원문 보존, 선택 함수 안 인용 필요, 다른 함수 인용만 있는 응답 거절, 잘못된 범위·수정 작업의 선택 거절을 포함한다.
- [Windows 개발 호스트](focused-explanation-development-integration.json): VS Code 1.96.4, 55개 흐름 통과. 새 흐름은 실제 문서·호스트·원문 선택·파일 편집/undo를 사용하지만 모델 답변은 제어된 HTTP 응답이다. 이전 54개와 새 1개를 확인했으며 실제 모델 품질 점수로 쓰지 않는다.
- [새 설치본](focused-explanation-installed-integration.json): 같은 VS Code에서 **55개 흐름 통과**, production 모드와 실제 설치 파일 11개 해시 일치. VSIX SHA-256 `5e087b7a1fca2b74c0c2b634854a42fd2e77334724f1188eb43b3d12621bded1`. 개발/설치의 같은 흐름을 110개의 별개 기능으로 합산하지 않는다. 웹·확장 빌드와 VSIX 패키징도 성공했다.
- 로컬 `release:package`·`release:check`에서 체크섬·소스 manifest·라이선스·VSIX와 저장소 밖으로 추출한 분석/Rust WASM·Python 측정·Python/Go/Java/C# 원문 도구 실행을 통과했다. 이후 추가한 검사 결과 문서는 이전 소스 ZIP에 포함됐다고 주장하지 않는다. 설치 VSIX와 실제 런타임 해시는 일치하며 공개 릴리스 게시는 하지 않았다.
- [한국어 화면](focused-explanation-ko.jpg), [영어 화면](focused-explanation-en.jpg): 실제 빌드 UI/worker, 공개 예제, 모의 편집기·제어된 답변. 읽던 함수로 진입, 범위 변경 시 이전 결과 제거, 이름·줄 범위·인용 표시와 선택기의 접근성 이름을 확인했다. 설치 VS Code의 수동 클릭 결과와 구분한다.
- 화면 검증 중 숫자 배열의 일반 합계를 결제 금액으로 부르던 기본 사전을 수정했다. `total → 합계 / Total`, `subtotal → 부분 합계 / Subtotal`, `amount → 값 / Amount` 등으로 바꿨다. 문맥을 이해하는 새 의미 분석기나 모든 용어 정확성 보장은 아니다.

전체 핵심 검사의 첫 실행은 SDK 경로 미설정으로 Java·Go·C# 준비에 실패했고, Python 3건·측정 실행기 1건도 시간 초과였다. **231 pass / 4 fail / 24 skipped, 5개 파일 실패**를 보존한다. 준비 실패 때문에 건너뛴 24개를 통과로 세지 않는다. SDK 경로를 설정한 직렬 후속 실행은 **258 pass / 1 fail**, 기존 Java 리터럴 사례의 30초 timeout이 남았다. 원인을 확정하거나 전체 통과로 표시하지 않는다. [기계 판독 기록](focused-explanation-verification.json)에 각 실행을 구분한다. 제품·테스트의 제한 시간이나 assertion을 완화하지 않았다.

## 동일 제품 소스의 Windows·Ubuntu CI

커밋 `9758dacdc0908d22966e7e6877c3639a3f8af13a`의 [Verify 실행](https://github.com/him55710-sudo/pureobom/actions/runs/39304019563)은 양쪽 운영체제 모두 성공했다. 각 로그에서 핵심 **259개**, 개발·production 설치 각각 **55개**, 설치 파일 **11개** 해시와 저장소 밖의 패키지 도구 실행을 확인했다. [CI 원자료](focused-explanation-ci.json)는 커밋·job·로그 해시·VSIX·런타임 파일 해시를 보존한다.

CI의 성공으로 로컬 두 실행을 통과로 바꾸거나 시간 초과의 원인이 해결됐다고 단정하지 않는다. CI에는 실제 사용자 프로젝트의 모델 추론이나 외부 프로젝트의 원래 테스트가 포함되지 않는다. stable/Pages 0.6.0 게시와도 별개다.

## 공개 판정

함수 선택·원문 위치 검증과 모델의 이해 능력은 별개다. 이번 실제 프로젝트 설명 성공 사례는 **0건**이며 정확도 비율을 계산할 수 없다. 기존 실제 서식 편집과 복구 결과는 그대로 유효하지만 전체 요청 완료·모든 언어·최적화·항상 빠른 로컬 실행을 보장하지 않는다. 평가는 구현한 에이전트가 수행했고 독립 제3자 사용자 실험은 아니다.
