# 풀어봄 제품 전략 — 2026-10-16

> **제품 우선 개발로 갱신:** 유료 API 없는 다언어 이해·수정·최적화와 실제 프로젝트 검증을 먼저 진행한다. 현재 구현 순서와 완료 기준은 [제품 완성 계획](PRODUCT_COMPLETION.md), 언어별 실제 범위는 [지원 표](LANGUAGE_SUPPORT.md), 에이전트의 변경과 검증은 [작업 기록](AGENT_WORKLOG.md)을 따른다. 아래 성장 계획은 이후 단계이며 개발의 선행 조건이 아니다.

## 지키는 기획

AI가 만든 코드를 비개발자가 자신의 언어로 읽고, 구조·표·연결 지도로 이해하며, 설명에서 수정해 실제 코드로 반영한다. 첫 제품은 사용자가 선택한 **VS Code 확장 기능**이다. 브라우저는 설치 전 체험과 독립적인 로컬 사용을 위한 보조 진입점이다.

한 문장: **“AI가 코드를 썼다면, 이제 내가 이해하고 고칠 차례.”**

영문: **“Read it. Change it. Check it.”**

## 첫 사용자를 좁힌다

첫 대상은 AI로 JS/TS 앱을 만들었지만 배송비, 체험 기간, 할인율 같은 규칙을 수정할 때마다 프롬프트를 반복하는 비개발 창업자·기획자다. 두 번째 대상은 해당 사람과 함께 검토하는 개발자·교육자다. 처음부터 모든 언어·모든 프레임워크·모든 리팩터링을 약속하지 않는다.

핵심 과제는 “내 앱의 무료 배송 기준을 바꾸면 6만 원 주문은 어떻게 되는가?”다. 완료 조건은 설명을 읽고 → 기준값을 선택하고 → 변경 전후 입력 표에서 영향을 보고 → 실제 diff를 확인해 적용·취소하는 것이다. 설명의 그럴듯함보다 **사용자의 수정 판단**이 제품 가치다.

## 지금 제공하는 차별점

| 질문 | 제품의 응답 |
| --- | --- |
| 설명이 실제 코드와 연결되나? | 구문 트리에서 추출한 위치로 원본 행에 이동한다. |
| 내가 바꿀 수 있나? | 표시된 값·비교 연산을 수정하고 해당 범위만 변경한다. |
| 어떤 사용자가 영향을 받나? | 사용자가 선택한 최대 12개 입력의 전후 결과를 표로 비교한다. |
| 모르는 것도 아는 척하나? | 미지원 구문과 계산 실패를 확인 불가로 표시한다. |
| 남에게 설명할 수 있나? | 실제 비교 표와 제한 사항을 Markdown으로 내보낸다. |
| 시작 비용은? | 계정·API 키 없이 예제로 시작하고, 원하면 자기 파일을 연다. |
| 이름이 내 업무와 다르면? | 원본 이름과 선언 위치를 보면서 내 용어를 붙이고, 그 용어로 규칙을 수정한다. |

여기서 “영향”은 **표시된 입력에서 확인한 출력 변화**만 뜻한다. 의존성 지도는 정적 import 관계이며 모든 런타임 영향이나 전체 회귀 안전성을 증명하지 않는다.

## 비교에서 배운 점

2026-10-16에 확인한 공식 저장소·문서를 기준으로 한 설계 참고이며 시장 점유율 조사나 수요 증명은 아니다.

- [CodeTour](https://github.com/microsoft/codetour)는 코드 위치에 연결된 안내를 제공한다. 풀어봄은 읽는 과정에 규칙 편집과 입력별 비교를 연결하는 데 집중한다.
- [VS Code Debug Visualizer](https://github.com/hediet/vscode-debug-visualizer)는 디버깅 중 데이터를 시각화한다. 풀어봄은 디버거를 설정하기 전 제한된 계산을 통해 첫 변경을 이해하도록 설계한다.
- [Excalidraw](https://github.com/excalidraw/excalidraw)의 공개 체험·사용 결과물 중심 소개에서 배울 수 있다. 이는 그 프로젝트의 성장 원인을 증명하는 주장이 아니다.
- [VS Code 배포 문서](https://code.visualstudio.com/api/working-with-extensions/publishing-extension)에 따라 VSIX 직접 설치와 Marketplace 게시를 구분한다. 현재 publisher는 로컬 설치용이며 Marketplace에 게시되었다고 표시하지 않는다.

## 확산을 제품 안에 넣는 방식

1. 공개 데모는 자기 코드를 올리기 전에 “바꾸기 → 달라지는 사례 확인”을 체험한다.
2. 예제 URL은 코드나 개인정보를 포함하지 않는다. `?demo=shipping&lang=en`은 준비된 예제만 연다.
3. 사용자가 만든 비교 설명서를 기획 문서·PR·수업에 가져갈 수 있다. 자동 업로드나 강제 홍보를 넣지 않는다.
4. 재현 가능한 작은 예제를 기여 단위로 삼는다. 사용자가 막힌 사례가 파서·번역·시나리오 개선으로 이어진다.

이 흐름은 확산 가설이다. 실제 공유율이나 재방문을 아직 측정하지 않았다. 스타 구매, 무관한 저장소 홍보 댓글, 허위 사용자·기업 로고·추천사는 사용하지 않는다.

## 1만 스타까지의 의사결정 기준

스타 1만 개는 장기적인 배포 성과 목표이며 코드만으로 보장할 수 없다. 2026-10-16의 [공개 상태 점검](LAUNCH_READINESS.md)에서는 스타·포크·공개 사용자 이슈가 0개이고 관찰 기록도 비어 있었다. 전환율·수요·재사용은 아직 검증되지 않았다. 아래 수치는 **출시 후 검증할 목표값**이고 달성 실적이 아니다.

| 단계 | 검증할 가설 | 진행 기준 | 실패하면 |
| --- | --- | --- | --- |
| 5명 관찰 | 설명에서 변경을 스스로 이해한다 | 5명 중 4명이 5분 안에 배송 예제 수정과 결과 설명, 도움 횟수 기록 | 설명·온보딩 수정 |
| 20명 실제 사용 | 예제 밖에서도 가치가 있다 | 20명 중 10명이 자기 코드에서 확인 가능한 변경 완료 | 지원 구문보다 핵심 과제 재검토 |
| 4주 사용 | 반복 문제가 해결된다 | 최초 활성 사용자 중 30%가 7일 안에 두 번째 실사용을 자발적으로 보고 | 반복 가치가 있는 시나리오 선택 |
| 공개 출시 | 체험이 설치와 기여로 연결된다 | 플랫폼별 링크 클릭·VSIX 다운로드·재현 이슈·기여자 수를 별도 기록 | 메시지 또는 설치 마찰 개선 |

참가자에게 사전 동의를 받고 작업 성공·이해 설명·오류·시간을 기록한다. 제품에 숨은 추적을 추가하지 않는다. 소규모 표본의 비율은 전체 시장 추정으로 사용하지 않는다. 다운로드는 사용자 수가 아니며 스타는 재사용 증거가 아니다.

## 이후 우선순위

1. 실제 사용에서 가장 많이 막히는 JS/TS 구문을 재현 사례와 함께 지원.
2. 0.4에 추가한 파일·선언별 사용자 용어를 실제 프로젝트에서 검증하고, 번역 기여 구조를 확장.
3. 0.6에서 VS Code가 보고한 현재 파일 타입 오류·경고를 연결했다. 프로젝트 전체의 변경 전후 검사와 완료 여부 판단은 여전히 후속 과제다. [범위와 재현 예제](EDITOR_REPORTS.md).
4. 선택형 AI 설명 어댑터: 전송 범위 동의, 키 보호, 소스 근거와 별도 표시.
5. Python 등 언어별 파서, 여러 파일을 묶은 의미 단위 변경, 격리된 실제 테스트 실행.

사용자 용어의 현재 범위는 [용어 안내](TERMINOLOGY.md)에 명시했다. 3의 전체 프로젝트 검사와 4~5는 현재 구현되었다고 광고하지 않는다. 장기적으로 시니어 개발자에 가까운 판단을 돕되 현재 버전을 그 수준의 대체재로 부르지 않는다.
