# 시스템 설계 워크스페이스 시작하기

[실제 성공·실패 기록 따라 보기](SYSTEM_WORKSPACE_DEMO.md) · [지원 환경과 범위](SYSTEM_WORKSPACE_SUPPORT.md)

이 안내는 `codex/system-design-workspace` 브랜치의 0.7 개발판을 대상으로 한다. 공개 0.6.0 VSIX와 hosted browser demo에는 시스템 설계 화면이 없다. 전체 요구사항과 검증 여부는 [기획](SYSTEM_WORKSPACE_PLAN.md)과 [상태 표](SYSTEM_WORKSPACE_STATUS.md)에 별도로 유지한다.

## 설치

Node.js 24와 pnpm 11.25.0이 있는 이 소스 폴더에서 실행한다.

```sh
pnpm install --frozen-lockfile
pnpm extension:build
pnpm extension:package
```

VS Code 확장 메뉴에서 **VSIX에서 설치**를 선택하고 `release/pureobom-0.7.0.vsix`를 연다. 왼쪽 풀어봄 아이콘의 **시스템 설계 시작 안내** 또는 같은 이름의 명령으로 설치본에 포함된 네 단계 안내를 연다. 신뢰한 로컬 Git 프로젝트의 최상위 폴더를 열고 안내의 **시스템 설계 열기**를 누른다. 구현하려면 첫 Git 커밋과 로그인된 Codex CLI, 프로젝트의 검사 명령이 필요하다. 모델을 연결하기 전에도 구조와 근거를 탐색할 수 있다. 안내의 체크 표시는 안내 열람·명령 실행 기록이며 구현 완료 판정이 아니다.

## 코드를 읽고 첫 수정 요청하기

워크스페이스는 읽기 화면으로 열립니다. Codex 연결을 확인하고 **내 코드를 쉬운 말로 읽기**를 누른 뒤, 쉬운 제목으로 읽고 싶은 파일을 고릅니다. 선택한 파일은 원문 전체를 나누어 목적·입출력·조건·예외·처리 순서·수정 방법을 해석합니다. **코드와 나란히 보기**로 각 설명에 해당하는 원문을 확인할 수 있습니다.

**이 요청으로 수정 준비하기**로 예시를 가져오거나 **이 부분을 내가 원하는 대로 바꾸기**로 직접 적습니다. 요청을 고친 뒤 **변경안 만들기**를 실행하고, 실제 변경 전후 설명과 검사 결과를 검토해 반영하거나 되돌립니다. 설명을 읽은 뒤 코드가 바뀌었다면 다시 읽어야 합니다. 작성 이유는 원문에 명시된 내용·추정·알 수 없는 내용을 구분합니다. AI 해석과 실제 실행 검사는 서로 다른 확인입니다.

이 파일별 상세 읽기는 현재 VS Code 개발판에 구현돼 있습니다. GitHub 링크·폴더를 가져오는 독립 앱은 아직 남아 있습니다. [현재 제품 기준](CODE_READING_PRODUCT.md).

## 구조와 고급 도구에서 설계 변경

설계 패널은 기능을 고르면 역할과 목표를, 규칙을 고르면 정책과 조건을, 함수를 고르면 입출력을 먼저 보여 준다. 긴 구현 기준과 나머지 항목은 펼쳐 확인할 수 있으며 접어도 저장 내용은 유지된다. [화면과 검증 기록](PROGRESSIVE_SPEC.md).

읽기 화면의 **구조와 고급 도구**를 누르면 설계와 탐색 도구가 나타납니다. 고급 화면의 **프로젝트 설명 읽기**로 돌아갈 수 있으며 작성하던 설계와 탐색 위치는 유지됩니다. 화면 전환만으로 모델을 실행하지 않습니다.

1. 왼쪽 트리나 검색으로 관련 코드를 찾는다. 파일·선언·규칙을 선택하고 근거에서 원문으로 이동한다. 편집기에서는 **풀어봄: 선택한 코드를 시스템에서 보기**로 돌아올 수 있다. 미해석 범위 안내도 함께 읽는다.
2. **업무 기능 만들기**에서 화면, 서버 액션/API, 공통 정책 등 실제로 연결된 코드 대상을 묶는다. 업무 기능의 이름과 경계는 사용자가 정한다. 폴더 이름만으로 업무 의미가 확정되지는 않는다.
3. 오른쪽 설계에 원하는 동작, 정책, 유지해야 하는 동작과 완료 기준을 쓴다. 예를 들어 현재 팀 owner만 구성원을 초대·제거하고, member는 명단을 조회하며, 직접 서버 요청도 같은 팀 권한으로 검사하도록 명시한다. 실제 프로젝트에 없는 역할이나 구조를 있다고 가정하지 않는다.
4. **설계만 저장**으로 명세만 확정할 수 있다. 코드 변경을 원할 때 **Codex 연결 확인**을 누르고, 전달 동의와 실제 `package.json` 검사 명령을 선택한다. 필요하면 **이 프로젝트에 보관**한다. 실행기 경로와 모델은 설정에서 확인한다.
5. **저장하고 구현**을 누른다. 별도 작업 복사본에서 관련 코드와 테스트를 변경한다. 작업 패널의 명령·파일 요청은 실제 범위를 읽고 허용하거나 거절한다. 에이전트가 끝난 뒤 제품이 선택한 검사를 다시 실행한다.
6. 변경 파일과 diff, 검사 로그, 범위 밖 파일과 검사 파일 변경을 읽는다. 각 완료 기준에 관찰한 결과와 근거를 기록한다. 명령이 통과했다는 이유로 브라우저 동작이나 전체 회귀까지 확인했다고 표시하지 않는다. 실패 기준은 반영을 막으며 미확인 기준은 명시적으로 수락해도 미확인으로 남는다.
7. **검토 기록 저장 → 검토한 변경 반영**을 실행한다. 구조와 관측 결과가 갱신되는지 확인한다. 원본이 바뀌면 이전 결과를 그대로 반영하지 않는다. 필요하면 **이번 변경 되돌리기**로 코드를 복원한다. 설계 목표는 삭제되지 않는다.

반영 뒤 목표를 충족했는지 검토하고, 필요할 때 **기준 코드 비교·다시 연결**에서 새 기준을 명시적으로 확정한다. 파일이 달라졌다는 관측만으로 자연어 목표가 충족됐다고 단정하지 않는다.

**설계와 코드 관측 비교**에서 저장 당시와 현재의 조건·선언·호출 연결을 펼쳐 볼 수 있다. 목표·완료 기준은 그대로 유지하며, 현재 코드 근거로 이동할 수 있다. 기록이 없는 이전 설계와 보관 한도는 [관측 비교 안내](WORKSPACE_OBSERVATIONS.md)를 확인한다.

탐색한 기능과 저장 설계, 펼친 트리, 검색어, 캔버스 배치는 프로젝트별로 보관한다. 하단에 **탐색 위치 기억함**이 표시되면 같은 프로필에서 다시 열어 이어 볼 수 있다. 코드가 사라졌을 때의 복원과 저장 실패 재시도는 [탐색 위치 안내](WORKSPACE_NAVIGATION.md)를 확인한다. 노드 배치를 바꾸는 것은 코드나 설계 목표를 변경하지 않는다.

## 실행과 검증의 범위

기본 분석은 로컬에서 처리한다. Codex 구현을 선택하면 설계와 필요한 프로젝트 코드가 연결된 모델에 전달되고, 선택한 명령이 실행된다. worktree는 파일 변경을 분리하며 보안 샌드박스를 대신하지 않는다. 운영 배포와 push는 이 흐름의 자동 단계가 아니다.

일반 자동 초안 저장은 구현을 시작하지 않는다. 초안은 [초안 복원 안내](DESIGN_DRAFTS.md), 실행 설정은 [연결·명령 선택](EXECUTION_SETTINGS.md), 기준별 검토는 [구현 검토](IMPLEMENTATION_REVIEW.md), 중단·충돌은 [복구 안내](AGENT_IMPLEMENTATION.md)를 확인한다. **창을 닫아도 구현은 계속된다.** 같은 프로젝트를 같은 편집기 프로필에서 열면 관리 프로세스의 작업·승인에 다시 연결한다. 중지하려면 `작업 취소`를 선택한다. 연결 오류에서는 `실행 상태 다시 연결`로 현재 상태를 확인한다. 관리 프로세스 자체가 사라진 경우 이전 승인을 재사용하거나 같은 구현을 자동으로 반복하지 않는다. [재연결 범위와 제한](MANAGED_AGENT_HOST.md).

재현 가능한 첫 외부 사례는 [Next.js SaaS Starter 팀 권한 변경](../validation/next-saas-starter/README.md)이다. 설치 UI, 실제 모델, 앱 브라우저, SQL 결과, 원본 복원은 각각의 증거 범위를 구분한다. [현재 상태](SYSTEM_WORKSPACE_STATUS.md)에 남은 검증을 전체 제품 완료로 바꾸지 않는다.
