# 결과 중심 앱 제안 — 거절된 이전 방향 기록

> 최신 사용자 정정으로 아래의 앱 미리보기 중심 제안은 채택하지 않는다. 현재 구현과 완료 기준은 [코드를 쉬운 설명으로 읽고 수정하기](CODE_READING_PRODUCT.md)다. 독립 앱과 GitHub·폴더 가져오기 요구는 유지하며, 첫 화면과 핵심 작업을 실제 코드 해석에 맞춘다.

2026-10-20. 사용자는 현재 화면이 훨씬 더 쉬워야 한다고 지적했고, AI 오케스트레이션 앱 Orca처럼 독립 앱을 제공하여 GitHub 링크·저장소·폴더를 넣으면 코드를 이해하기 쉽게 설명하는 방향을 제안했다.

같은 날 사용자는 구조도 자체가 마음에 들지 않으며, 비개발자는 AI가 일을 해주고 부족하거나 수정하고 싶은 부분을 보기 좋게 보여주기를 원한다고 명확히 수정했다. **파일 구조·파일명 탐색을 기본 경험에서 제외하는 것이 현재 요구다.** 앞선 “첫 설명 → 기능 탐색” 제안도 이 요구에 맞게 수정한다. 이 사용자 요구를 비개발자 전체에 대해 검증된 시장 조사 결과로 확대하지 않는다.

제품 정의: **기존 앱을 가져오면 AI가 원하는 결과를 만들고, 사용자는 실제 모습과 동작을 보면서 필요한 부분만 더 바꾸는 앱.**

아래 내용은 구현할 경험과 수용 기준이다. 독립 앱·실행 화면·자동 점검이 이미 연결됐다는 보고가 아니다. 기존 기획 원문은 역사적 기준으로 보존하되, 구조도 우선순위는 최신 요구로 대체한다.

## 제안하는 기본 경험

1. **프로젝트 넣기.** 첫 화면의 큰 영역에 폴더를 끌어 놓거나 GitHub 주소를 붙인다. 폴더 선택 버튼과 최근 프로젝트도 제공한다. 폴더는 현재 위치에서 읽고, 원격 저장소는 앱이 관리하는 작업 사본으로 가져온다.
2. **내 앱의 결과 보기.** 준비 가능한 프로젝트는 실제 실행 화면을 가장 크게 보여준다. 사용자 목표와 관련된 화면으로 이동하고 직접 눌러볼 수 있어야 한다. 실행하지 못하면 그 이유와 필요한 조치를 쉬운 말로 표시한다. 코드 요약이나 만들어낸 화면을 실제 실행 결과로 대신하지 않는다.
3. **AI가 작업을 맡기.** “예약을 더 쉽게 만들어줘”처럼 원하는 결과를 받으면 AI가 필요한 코드 탐색·계획·수정·검사를 수행한다. 사용자가 파일이나 담당 에이전트를 고르는 절차는 없다. 목표가 없으면 실제 근거가 있는 개선 제안을 소수로 우선 보여준다. 취향에 따른 제안과 재현한 문제를 구분한다.
4. **부족한 부분과 원하는 수정만 짚기.** “날짜를 빠뜨렸을 때 안내가 어려워요”처럼 사용자가 겪는 현상으로 설명하고 해당 화면·동작을 연결한다. 화면을 짚거나 “이 버튼을 더 크게”, “가입 절차를 짧게”라고 말할 수 있게 한다. 파일별 설명을 이름만 바꿔 나열하지 않는다.
5. **결과를 비교하고 반영하기.** 변경 전후 화면·동작과 실제 검사 결과를 먼저 보여준다. 사용자는 결과를 써보고 “이 모습 사용하기”, “이 부분만 다시”, “되돌리기”로 진행한다. 화면에 보이지 않는 권한·저장·계산 같은 변경도 실제 사용 사례와 관찰한 결과로 설명한다.

코드 분석·다중 파일 구현·검사·검토·복구 연결은 이 경험을 지탱하는 내부 기능이다. 기술 상세는 필요할 때만 열 수 있다. 사용자가 기술 상세를 학습하거나 모든 설계 항목을 채워야 진행할 수 있게 만들지 않는다. 금액·권한·데이터 삭제처럼 결과가 큰 결정은 사용자가 이해할 수 있는 선택으로 필요한 시점에 확인한다.

## 화면 예시와 아직 없는 기능

[결과 중심 화면 예시](prototypes/result-first-app.html)는 가상의 예약 앱으로 다음 경험을 검토하는 HTML 조각이다. 자체 실행 앱이나 실제 분석 결과가 아니다.

- 세 가지 제안에서 해당 화면 위치를 확인한다.
- 준비된 개선안을 열고 기존 화면과 비교한다.
- 인원에 따른 금액·날짜 누락 안내를 직접 눌러본다.
- 예시 안에서 결과 선택·되돌리기와 수정 요청 남기기를 수행한다.

모델 호출·실제 코드 수정·프로젝트 실행·검사·배포는 수행하지 않는다. “다듬은 모습 보기”는 미리 작성된 예시를 전환하며 입력한 추가 요청을 구현하지 않는다. 실제 AI 결과로 오인하지 않도록 화면에도 이 한계를 표시한다.

현재 `ProjectReader`의 파일 설명·불확실성 목록에는 실행 점검에서 발견한 문제나 화면 좌표가 없다. 이를 곧바로 “발견된 문제”로 표시하면 안 된다. 실제 구현에는 실행 준비, 화면과 사용자 동작 수집, 근거 있는 문제 기록, 작업 전후 비교를 기존 수정·검사·복구 서비스와 연결하는 작업이 남아 있다.

## Orca에서 참고할 점

[Orca 공식 안내](https://www.onorca.dev/)는 여러 코딩 에이전트, 작업 공간, 터미널, diff, 브라우저를 하나의 앱에서 다룬다. 독립 앱과 작업 관리 방식을 참고할 수 있다. 풀어봄의 기본 화면은 실제 앱과 원하는 결과에 집중하고, 에이전트 선택·병렬 작업·상세 실행 관리는 필요한 경우에만 연다.

GitHub 저장소를 설명과 구조도로 바꾸는 기능은 이미 [GitDiagram](https://github.com/ahmedkhaleel2004/gitdiagram)에도 있다. 단순히 독립 창을 제공하거나 저장소 요약을 생성하는 것만으로 차별성을 주장하지 않는다. 사용자가 코드 탐색 없이 원하는 결과를 얻고 수정할 수 있는지는 아직 검증해야 할 제품 가설이다.

## 현재 구현에서 재사용할 것

- `src/workspace/analyze.ts`와 구조·관계·설계 모델은 공급받은 코드에서 분석하므로 독립 앱에서도 재사용할 후보이다.
- 기존 React 기반 읽기·구조 화면과 초안·변경 검토의 일부를 공유할 수 있다. 기본 화면의 정보 순서와 표현은 다시 설계한다.
- `extension/src/designWorkspace.ts`의 폴더 수집, 메시지 전달, 소스 열기, 저장 위치, 작업 실행은 VS Code에 연결돼 있다. 이를 공통 서비스와 앱별 연결 코드로 분리해야 한다.
- 실제 수정·검사·취소·오래된 결과 차단·부분 반영 복구의 보장을 독립 앱에서도 검증한다. VS Code에서 통과했다는 사실로 독립 앱의 완성을 주장하지 않는다.

앱 껍데기만 바꿔 현재 복잡한 화면을 그대로 옮기는 것으로 완료 처리하지 않는다.

## 구현을 시작할 때 확인할 결과

- VS Code를 설치하거나 실행하지 않고 앱에서 로컬 폴더와 GitHub 저장소를 열 수 있다.
- 원본을 옮기거나 변경하지 않고 프로젝트를 살펴볼 수 있다. 처음 열었다는 이유만으로 사용자 코드나 설치 스크립트를 임의로 실행하지 않는다. 앱 실행은 필요한 접근과 준비 상태를 확인한 작업 사본에서 한다.
- 첫 작업을 완료할 때 파일명·폴더 구조·그래프 노드·기술 설계 입력을 요구하지 않는다.
- 실제 실행 화면이나 검증한 사용자 동작과 제안의 근거를 연결한다. 코드에서 추정한 문제는 확인되지 않았다고 표시한다.
- AI가 만든 개선안과 사용자의 추가 요청이 실제 수정·검사·복구까지 이어진다. 정해진 예시 화면 전환을 구현 성공으로 세지 않는다.
- 처음 화면에서 터미널·브랜치·심볼·스키마를 알아야만 진행하는 단계가 없다. 인증이나 모델 연결은 필요한 시점에 쉬운 안내로 제공한다.
- 읽지 못한 파일·분석 제한·모델 설명 실패를 숨기지 않는다. 큰 저장소를 일부만 읽었으면 전체 분석으로 표시하지 않는다.
- 화면 없는 기능도 사용자에게 영향을 주는 동작의 전후 결과로 검토할 수 있다.
- 변경 완료 표시에는 실제 수행한 검사와 아직 확인하지 못한 동작이 포함된다.
- 실제 사람의 이해도·도움 요청·과제 완료 여부는 별도 측정한다. 현재 참가자 결과는 없다.
