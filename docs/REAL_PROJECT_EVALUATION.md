# 사용자의 실제 프로젝트로 평가하기

풀어봄이 만든 예제나 의도적으로 삽입한 오류를 잡는 검사는 기본 회귀 검사다. 사용자가 만든 프로젝트에서 코드 이해·수정·검증에 도움이 되는지는 **사용자가 선택한 실제 저장소의 실제 유지보수 과제**로 별도 평가한다. 이 문서는 평가 절차이며 모든 항목을 제품이 자동 판정한다는 뜻이 아니다.

## 먼저 고정할 것

저장소 버전·대상 파일·목적·기존 검사 명령을 수정 전에 기록한다. 로컬 미커밋 파일과 GitHub 버전이 다르면 어느 상태를 평가하는지 명시한다. 평가 때문에 원래 작업물을 덮어쓰지 않는다. 실제 버그가 확인되지 않았다면 버그를 만들어 넣지 않고, 사용자가 필요한 변경 또는 가독성 개선 같은 유지보수 과제를 선택한다. 이미 실패하는 검사도 기준선에 보존한다.

비공개 프로젝트의 소스·모델 응답·경로·보고서는 로컬 또는 그 프로젝트가 승인한 장소에 보관한다. 공개 오픈소스 제품의 작업 기록에는 개인정보·비공개 소스 없이 방법과 제품 결함을 남긴다. 사용자가 저장소 접근을 허용한 것과 공개 사례 게시를 허용한 것은 다르다.

## 판정 항목

| 항목 | 실제 근거 | 이 근거만으로 말할 수 없는 것 |
| --- | --- | --- |
| 파일 읽기 | 선정 기준, 전체 파일 수, 읽기/문법 오류, 생략·미지원 범위 | 설명 정확도, 프로젝트 전체 이해 |
| 설명 | 실제 인용 범위·줄, 조건의 양쪽 결과·예외·반환·단위·외부 의존성 대조 | 모델의 요약을 그대로 정답으로 채점 |
| 수정 의도 | 변경 전 명시한 요청, diff, 요청 밖 변경 수, 검토자와 판정 | 테스트 통과만으로 요청 달성 |
| 기존 동작 | 동일 명령·환경의 변경 전/후 결과, 실제 테스트 수·실패 목록 | 종료 코드 0을 모든 동작의 정확성으로 해석 |
| 편집기 연동 | 실제 원문 이동·native diff·명시적 적용·미저장 차단·undo·디스크 복구 | CLI 파싱 성공을 편집기 사용 성공으로 해석 |
| 성능 | 필요한 경우에만 반복 가능한 입력과 동일 결과, 전후 시간/메모리 원자료 | 한 번의 테스트 시간, 가독성 변경을 최적화로 부르기 |
| 사용성 | 실제 사용자의 과제 수행 여부, 잘못 이해한 설명, 막힌 단계·도움 요청 | 에이전트의 API 검사를 비개발자 사용성 인증으로 부르기 |

정확한 코드 인용과 올바른 설명도 다르다. 모델이 실제 코드를 인용하면서 의미·단위·조건을 틀릴 수 있으므로 별도로 검토한다. 에이전트가 검토한 경우 그 사실을 밝히며 독립적인 제3자 평가나 사용자 실험으로 표시하지 않는다.

## 실행 순서

1. 원본 상태·도구 환경·기존 테스트 결과를 기록한다. 의존성이 없거나 검사가 시작되지 못한 실패를 제품의 통과 기록에 넣지 않는다.
2. 실제 소스를 풀어봄으로 읽는다. 일부 파일만 고르면 선정 이유를 기록하고, 전체 코퍼스를 평가했을 때만 전체 수치를 제시한다. 설명 한도와 미지원 문법을 숨기지 않는다.
3. 실제 유지보수 요청을 입력한다. 모델·digest·요청·응답·검증 오류를 로컬에 남긴다. 거절이나 실패 뒤에 다시 시도하면 앞선 실패도 보존한다.
4. diff에서 요청 범위와 의미를 검토한다. 형식 정리라면 가능할 때 AST·토큰의 동일성도 대조한다. 개발판의 JS/TS 제안은 원본과 후보의 코드 내용·구조·주석 및 중괄호 수를 별도로 표시한다. 문법이 맞아도 요청 밖 변경이 있으면 거절하고 적용 전 단계를 실패로 기록한다. 이 확인이 일반적인 의미 동등성 증명으로 확대되지는 않는다.
5. 실제 편집기에서 적용하고 같은 기존 테스트를 실행한다. 파일 내용·명령·환경이 달라져 결과 비교가 무효라면 그 이유를 기록한다.
6. undo 후 원본 해시와 기존 검사를 다시 확인한다. 최종 반영할 변경과 평가용 변경은 구분한다.
7. **확인됨 / 실패 / 일부만 확인 / 미검증**을 항목별로 적는다. 전체 점수 하나로 남은 결함을 가리지 않는다.

제품의 [기존 프로젝트 명령 연결](PROJECT_CHECKS.md), [전후 성능 측정](BENCHMARKS.md), [지원 범위](LANGUAGE_SUPPORT.md)를 함께 사용한다. 원래 프로젝트가 작성한 검사를 재사용하는 것은 허용되며, 풀어봄 평가를 위해 임의 오류를 심는 사례와 구분한다. 과학·의료·재무 등 도메인 모델의 타당성은 소프트웨어 편집·테스트 연동과 별개의 검증이다.

## 최소 보고서

보고서에는 대상 버전과 선정 이유, 실제 요청, 실행 환경, 변경 전/후/복구 결과, 설명 오류, 요청 밖 변경, 적용하지 않은 이유, 성능 측정 여부, 원본 복구 여부, 검토자와 미검증 범위를 넣는다. 테스트 개수·파서 지원 구문 수·모델 응답 수를 합쳐 사용자 효용 점수로 만들지 않는다.
